## 1부: 도입 - 왜 이 개념들이 중요한가? (5분)

### 🎬 오프닝: 여러분의 하루를 떠올려봅시다

아침에 일어나서 스마트폰을 봅니다. 카카오톡 알림이 와 있고, 유튜브 음악이 재생 중이며, 백그라운드에서 앱 업데이트가 다운로드되고 있습니다. **동시에** 세 가지 일이 일어나고 있죠.

그런데 잠깐, 여러분의 스마트폰 CPU는 (간단히 말해서) **한 번에 하나의 일만** 할 수 있습니다.

**어떻게 이게 가능할까요?** 🤔

### 🍳 비유: "혼밥 요리사"

혼자 사는 자취생이 저녁을 준비한다고 상상해보세요:

```
🍳 라면 끓이기 (3분)
🥚 계란 프라이 (2분)
🥗 샐러드 준비 (1분)
```

요리사(CPU)는 한 명인데, 세 요리를 "동시에" 완성해야 합니다.

**방법 1: 순차적으로** (FCFS)
- 라면 다 끓이고 → 계란 다 굽고 → 샐러드 만들기
- 결과: 라면 식음 😢

**방법 2: 번갈아가며** (Round Robin)
- 라면 물 올리고 → 계란 팬에 올리고 → 샐러드 야채 썰고 → 라면 스프 넣고...
- 결과: 모든 음식이 따뜻하게 완성! 🎉

**이것이 바로 CPU 스케줄링입니다!**

CPU도 마찬가지로 여러 프로그램을 아주 빠르게 왔다 갔다 하면서 실행합니다. 너무 빨라서 우리 눈에는 "동시에" 실행되는 것처럼 보이는 거죠.

### 왜 지금 이 개념들이 중요한가?

#### 1. 멀티코어 시대의 도래
- 2005년 이전: 단일 코어 CPU, 클럭 속도 경쟁
- 2005년 이후: Intel Core Duo 출시, 멀티코어 시대 시작
- 현재: 일반 노트북도 8-16코어, 서버는 64-128코어
- **문제**: 멀티코어를 활용하지 못하면 성능 향상 불가

#### 2. 클라우드 네이티브 아키텍처
우리가 다루는 AWS CDK 프로젝트를 생각해봅시다:
- **컨테이너화**: Docker/ECS에서 프로세스 격리가 핵심
- **서버리스**: Lambda 함수의 동시 실행 = 스레드 풀 관리
- **오토스케일링**: CPU 사용률 기반 = 스케줄링 효율성 측정
- **비용 최적화**: CPU 할당 이해 → 적절한 인스턴스 타입 선택

#### 3. 성능이 곧 비즈니스 가치
- Google 연구: 페이지 로딩 0.1초 지연 → 매출 1% 감소
- Amazon: 100ms 지연 → 매출 1% 감소
- Netflix: 스트리밍 버퍼링 1초 → 사용자 이탈률 증가

## 2부: 프로세스 vs 스레드 - 실행 모델의 심층 비교 (15분)

### 2.1 핵심 비유: 🏠 "아파트 vs 쉐어하우스"

프로세스와 스레드의 차이를 이해하는 가장 쉬운 방법은 **주거 형태**에 비유하는 것입니다.

#### 🏢 프로세스 = 개인 아파트

```
[1인 가구 A의 아파트]    [1인 가구 B의 아파트]
┌─────────────────┐    ┌─────────────────┐
│ 🛋️ 거실         │    │ 🛋️ 거실         │
│ 🍳 주방         │    │ 🍳 주방         │
│ 🚿 욕실         │    │ 🚿 욕실         │
│ 🔑 현관문       │    │ 🔑 현관문       │
└─────────────────┘    └─────────────────┘
   완전히 분리됨           완전히 분리됨
```

**특징**:
- 🔒 **완전한 독립**: A의 냉장고 음식을 B가 먹을 수 없음
- 💰 **비용이 높음**: 각자 월세, 관리비, 가전제품 필요
- 🔐 **보안 좋음**: 이웃이 망해도 나는 안전
- 📞 **소통 불편**: 옆집에 말 걸려면 초인종 눌러야 함 (IPC)

#### 🏠 스레드 = 쉐어하우스 (룸메이트)

```
[한 아파트에 3명의 룸메이트]
┌─────────────────────────────┐
│   🛋️ 공유 거실              │
│   🍳 공유 주방              │
│   🚿 공유 욕실              │
├─────────┬─────────┬─────────┤
│ 🛏️ A방  │ 🛏️ B방  │ 🛏️ C방  │
│ (개인)  │ (개인)  │ (개인)  │
└─────────┴─────────┴─────────┘
  각자 침실만 분리, 나머지 공유
```

**특징**:
- 🤝 **자원 공유**: 냉장고, TV, 와이파이 함께 사용
- 💵 **비용 절약**: 월세/관리비 n분의 1
- ⚡ **소통 쉬움**: 거실에서 바로 대화 가능
- ⚠️ **충돌 가능**: "누가 우유 다 마셨어?!" (Race Condition)
- 💥 **한 명 문제 = 전체 문제**: 룸메이트가 집을 어지럽히면 모두 피해

### 2.2 정식 정의

#### 프로세스(Process)

**정의**: 실행 중인 프로그램의 인스턴스

쉽게 말해, 여러분이 **크롬 브라우저를 실행**하면 그게 하나의 프로세스입니다.
크롬을 하나 더 실행하면? **또 다른 프로세스**가 생깁니다.

```
[프로세스 메모리 레이아웃 - 프로세스의 "아파트 구조"]
┌─────────────────────┐
│   스택 (Stack)      │ ← 함수 호출할 때 쌓이는 것 (접시 쌓기처럼)
│        ↓            │
│                     │
│        ↑            │
│   힙 (Heap)         │ ← new, malloc으로 동적 할당하는 공간
├─────────────────────┤
│   데이터 (Data)     │ ← 전역 변수들이 사는 곳
├─────────────────────┤
│   코드 (Code)       │ ← 우리가 작성한 프로그램 코드
└─────────────────────┘
```

#### 스레드(Thread)

**정의**: 프로세스 안에서 실제로 일하는 **일꾼**

하나의 프로세스 안에 여러 스레드가 있을 수 있습니다.
마치 **한 회사(프로세스) 안에 여러 직원(스레드)**이 있는 것처럼요.

**핵심**: 스레드들은 **Code, Data, Heap을 공유**하고, **Stack만 각자** 가집니다.

### 2.3 📊 한눈에 보는 비교표

| 측면 | 프로세스 (아파트) | 스레드 (쉐어하우스) |
|-----|-----------------|-------------------|
| 메모리 | 🏠 각자 독립 공간 | 🏠 거실 공유, 방만 분리 |
| 생성 비용 | 💸💸💸 비쌈 (이사 = 짐 많음) | 💸 저렴 (방만 추가) |
| 통신 | 📞 전화해야 함 (느림) | 🗣️ 그냥 말하면 됨 (빠름) |
| 안전성 | 🔒 옆집 불나도 OK | ⚠️ 룸메이트 실수 = 다 같이 피해 |
| 활용 | 완전히 다른 앱 | 같은 앱의 여러 기능 |

### 2.4 🎮 실생활 예시로 이해하기

#### 예시 1: 웹 브라우저

**Chrome 브라우저를 사용할 때:**

```
┌─────────────────────────────────────────────┐
│              Chrome (메인 프로세스)           │
│  - 주소창, 북마크, 설정 관리                   │
└─────────────────────────────────────────────┘
         ↓           ↓           ↓
    ┌─────────┐ ┌─────────┐ ┌─────────┐
    │ 탭1     │ │ 탭2     │ │ 탭3     │
    │ 유튜브  │ │ 네이버   │ │ 구글    │
    │(프로세스)│ │(프로세스)│ │(프로세스)│
    └─────────┘ └─────────┘ └─────────┘
```

**왜 각 탭이 별도 프로세스일까요?**
- 유튜브 탭이 멈춰도 → 네이버 탭은 정상 작동! ✅
- 악성 사이트가 있어도 → 다른 탭의 정보 접근 불가! 🔒

**각 탭 안에서는 스레드를 사용:**
- 동영상 재생 스레드
- 댓글 로딩 스레드
- 광고 표시 스레드

#### 예시 2: 카카오톡

```
┌─────────────────────────────────────────────┐
│           카카오톡 (하나의 프로세스)           │
├─────────────────────────────────────────────┤
│  스레드1: 메시지 수신 (24시간 대기)            │
│  스레드2: 이미지 다운로드                      │
│  스레드3: 알림 표시                           │
│  스레드4: 채팅방 UI 업데이트                   │
│                                             │
│  [공유 데이터: 친구 목록, 채팅 기록]            │
└─────────────────────────────────────────────┘
```

**왜 스레드를 사용할까요?**
- 이미지 다운로드 중에도 메시지 입력 가능! ⌨️
- 알림이 오면서 동시에 채팅방 스크롤 가능! 📱
- 친구 목록을 모든 스레드가 함께 사용 (메모리 절약)

#### 예시 3: 배달의민족 앱

```
[멀티스레딩의 장점]

싱글 스레드라면:
1. 지도 로딩 → (멈춤) →
2. 음식점 목록 로딩 → (멈춤) →
3. 리뷰 불러오기 → (멈춤) →
총 6초 (답답함 😤)

멀티 스레드라면:
동시에 시작:
├── 스레드1: 지도 로딩 (2초)
├── 스레드2: 음식점 목록 (2초)
└── 스레드3: 리뷰 불러오기 (2초)
총 2초! (앱이 빠르게 느껴짐 😊)
```

### 2.5 🔧 기술적 상세 (관심 있는 분들을 위해)

#### 생성 비용 실제 측정

실제로 얼마나 차이가 날까요?

```
[벤치마크 결과 - Linux 환경]

프로세스 생성 (fork):  약 100-500 μs (마이크로초)
스레드 생성:           약 5-20 μs

→ 스레드가 10~100배 빠름!
```

**비유**:
- 프로세스 생성 = 새 아파트 계약하고 이사하기 (서류, 짐 옮기기...)
- 스레드 생성 = 쉐어하우스에 방 하나 추가하기 (침대만 놓으면 됨)

#### 컨텍스트 스위칭 (작업 전환)

**비유: 📖 책 바꿔 읽기**

**프로세스 전환** = 완전히 다른 책으로 바꾸기
- 지금 읽던 책에 책갈피 끼우고
- 책장에 넣고
- 다른 책 찾아서 꺼내고
- 어디까지 읽었는지 책갈피 확인하고
- 읽기 시작
→ **시간이 많이 걸림!**

**스레드 전환** = 같은 책의 다른 챕터로 이동
- 현재 페이지 기억하고
- 다른 챕터로 점프
→ **훨씬 빠름!**

기술적으로는:
- 프로세스 전환: TLB(메모리 캐시) 전체 비움 → 느림
- 스레드 전환: TLB 유지 가능 → 빠름

### 2.6 🔢 성능 숫자로 비교

**생성 속도 (새로 만드는 시간)**:
```
프로세스 생성: 약 0.5ms (밀리초)
스레드 생성:   약 0.01ms

→ 스레드가 50배 빠름!
```

**비유**:
- 프로세스 생성 = 새 아파트 계약 (서류, 이사, 정리...)
- 스레드 생성 = 방에 침대 하나 추가 (금방 끝!)

**작업 전환 속도 (컨텍스트 스위칭)**:
```
프로세스 전환: 약 0.01ms
스레드 전환:   약 0.001ms

→ 스레드가 10배 빠름!
```

### 2.7 🗣️ 통신 방식 비교

**프로세스 간 통신** (아파트 간 대화):
```
🏢A → 📞전화 → 🏢B

방법: 파이프, 소켓, 공유 메모리, 메시지 큐
특징: 복잡하지만 안전
```

**스레드 간 통신** (룸메이트 간 대화):
```
🧑A → 🗣️"야" → 🧑B

방법: 그냥 변수 공유하면 됨
특징: 간단하지만 주의 필요! (동시에 수정하면 문제)
```

### 2.8 💥 Race Condition (경쟁 상태) 문제

**비유: 공용 냉장고의 우유** 🥛

```
[문제 상황]
룸메이트 A: "우유 없네, 마트 가야지"
룸메이트 B: "우유 없네, 마트 가야지"

(둘 다 마트 감)

결과: 우유가 2개! 😱
```

**프로그래밍에서**:
```
스레드 A: balance = 1000 읽음
스레드 B: balance = 1000 읽음

스레드 A: balance = 1000 + 500 저장 (입금)
스레드 B: balance = 1000 - 200 저장 (출금)

결과: balance = 800 (500원 입금이 사라짐!) 😱
```

**해결: 락(Lock)** 🔒
```
"냉장고 확인 중" 메모 붙이기 → 다른 사람 대기
확인 끝나면 메모 떼기

= mutex.lock() / mutex.unlock()
```

## 3부: CPU 스케줄링 알고리즘 - 실행 순서를 결정하는 정책 (10분)

### 3.1 🏦 핵심 비유: 은행 창구 시스템

CPU 스케줄링을 이해하는 가장 좋은 방법은 **은행 창구**에 비유하는 것입니다.

```
        [은행 = 컴퓨터]

🧑‍💼 창구 직원 = CPU (한 번에 한 명만 상대)
🧑‍🤝‍🧑 대기 고객들 = 실행 대기 중인 프로세스들
📋 번호표 시스템 = CPU 스케줄링 알고리즘

질문: 50명이 기다리고 있는데, 누구를 먼저 처리할까요?
```

**스케줄링이 필요한 이유**:
- CPU(창구 직원)는 한 번에 하나의 작업만 처리
- 하지만 대기 중인 프로세스(고객)는 수십~수백 개
- **어떤 순서로 처리하느냐에 따라 효율이 완전히 달라짐!**

### 3.2 📊 스케줄링의 목표 (은행으로 비유)

| 목표 | 컴퓨터 용어 | 은행 비유 |
|-----|-----------|----------|
| CPU 열심히 쓰기 | CPU 이용률 | 직원이 쉬지 않고 일하기 |
| 많이 처리하기 | 처리량(Throughput) | 하루에 더 많은 고객 처리 |
| 빨리 끝내기 | 반환 시간 | 고객의 총 방문 시간 줄이기 |
| 덜 기다리기 | 대기 시간 | 줄 서서 기다리는 시간 줄이기 |
| 빨리 반응하기 | 응답 시간 | "다음 분~" 불리기까지 시간 |

### 3.3 ⚔️ 선점형 vs 비선점형

**비선점형 = 양보 없는 은행**
- 한 번 창구에 앉으면 일 끝날 때까지 자리 독점
- 1시간 걸리는 복잡한 업무 → 뒷사람은 계속 기다림 😤

**선점형 = 공정한 은행**
- "손님, 10분 경과했으니 다음 분 먼저 모시고 다시 오세요"
- 모든 고객이 적절히 서비스 받음 😊

👉 **현대 OS는 대부분 선점형** (공정성 + 반응성)

### 3.4 🎯 주요 스케줄링 알고리즘 - 비유로 이해하기

#### 1️⃣ FCFS (First Come First Served) - 선착순

**비유: 일반 은행 번호표** 🎫

먼저 온 순서대로 처리합니다. 단순하죠!

```
🏦 은행 상황:
- 고객 A: 대출 상담 (30분 소요)
- 고객 B: 통장 재발급 (5분)
- 고객 C: 잔액 확인 (2분)

[FCFS 처리 순서]
A → B → C (도착한 순서대로)

[결과]
- A: 0분 대기, 30분 후 완료
- B: 30분 대기 😢, 35분 후 완료
- C: 35분 대기 😭, 37분 후 완료

평균 대기 시간: (0 + 30 + 35) / 3 = 21.7분
```

**문제: 호송 효과(Convoy Effect)** 🚌
- 버스(긴 작업) 하나가 뒤의 승용차(짧은 작업)들을 다 막음
- 잔액 확인 2분인데 30분 기다린 C 고객은 화남 😤

**실제 사용처**: 프린터 대기열 (먼저 보낸 문서부터 출력)

---

#### 2️⃣ SJF (Shortest Job First) - 짧은 일 먼저

**비유: 마트 계산대 "10개 이하 전용 레인"** 🛒

```
🏦 은행 상황 (같은 고객들):
- 고객 A: 대출 상담 (30분)
- 고객 B: 통장 재발급 (5분)
- 고객 C: 잔액 확인 (2분)

[SJF 처리 순서]
C → B → A (짧은 일부터!)

[결과]
- C: 0분 대기, 2분 후 완료 ✨
- B: 2분 대기, 7분 후 완료 ✨
- A: 7분 대기, 37분 후 완료

평균 대기 시간: (0 + 2 + 7) / 3 = 3분!!
```

**수학적으로 증명된 최적!** 📐
- 평균 대기 시간이 가장 짧음
- 단, 미래 예측이 필요함 (이 고객이 얼마나 걸릴지 어떻게 알아?)

**문제: 기아 현상(Starvation)** 😵
- 대출 상담 고객은 계속 뒤로 밀림
- "짧은 일" 고객이 계속 오면 영원히 서비스 못 받음

**해결: 에이징(Aging)** 👴
- 오래 기다린 고객의 우선순위를 점점 높임
- "10분 기다릴 때마다 VIP 등급 +1"

---

#### 3️⃣ Round Robin (RR) - 공평하게 돌아가며

**비유: 놀이공원 회전목마** 🎠

```
🎠 규칙:
- 모든 사람이 3분씩만 타고 내림
- 다 타고 싶으면 다시 줄 섬

[상황]
- 철수: 15분 타고 싶음
- 영희: 4분 타고 싶음
- 민수: 2분 타고 싶음

[RR 진행 (3분씩)]
0분: 철수 탑승 (3분)
3분: 영희 탑승 (3분)
6분: 민수 탑승 (2분 → 완료! ✅)
8분: 철수 탑승 (3분)
11분: 영희 탑승 (1분 → 완료! ✅)
12분: 철수 탑승 (3분)
15분: 철수 탑승 (3분)
18분: 철수 탑승 (3분 → 완료! ✅)

모든 사람이 비교적 공평하게 서비스 받음!
```

**Time Quantum(시간 할당량) 선택이 중요!**

```
⏱️ Time Quantum = 3분이라면:

너무 짧으면 (0.1분):
- 타자마자 내림, 다시 줄 섬
- 줄 서는 시간(오버헤드)이 더 많아짐 😵

너무 길면 (100분):
- 한 번 타면 오래 탐
- FCFS랑 똑같아짐, 뒷사람 답답 😤

적절하면 (3-5분):
- 모두가 적당히 서비스 받음 👍
```

**실제 사용처**:
- 윈도우/맥의 앱들 (카카오톡, 유튜브, VSCode가 동시에 돌아가는 것처럼 보임)

---

#### 4️⃣ 우선순위 스케줄링 - VIP 먼저

**비유: 공항 탑승** ✈️

```
✈️ 탑승 순서:
1순위: 🥇 퍼스트클래스
2순위: 🥈 비즈니스클래스
3순위: 🥉 이코노미클래스

[결과]
- 퍼스트 고객: 바로 탑승 ✨
- 비즈니스 고객: 조금 대기
- 이코노미 고객: 많이 대기 😢

→ 중요한 프로세스(시스템)를 먼저 처리
```

**문제: 기아 현상**
- 퍼스트 고객이 계속 오면? 이코노미는 못 탐 😭

**해결: 에이징**
- 30분 기다린 이코노미 → 비즈니스로 업그레이드!
- 1시간 기다린 이코노미 → 퍼스트로 업그레이드!

---

#### 5️⃣ 다단계 피드백 큐 - 적응형 시스템

**비유: 🎮 게임의 자동 난이도 조절**

게임이 플레이어의 실력을 보고 난이도를 자동 조절하듯이,
OS도 프로세스의 특성을 보고 대우를 바꿉니다.

```
[3단계 큐 시스템]

🥇 1층 (VIP): 빠른 응답 (RR, 8ms)
     ↓ (시간 초과하면 강등)
🥈 2층 (일반): 중간 (RR, 16ms)
     ↓ (또 시간 초과하면 강등)
🥉 3층 (경제석): 느려도 OK (FCFS)

[자동 분류 원리]
- 카톡 알림 (빨리 끝남) → 1층에서 처리 완료 ✨
- 유튜브 재생 (빨리 끝남) → 1층에서 처리 완료 ✨
- 동영상 인코딩 (오래 걸림) → 1층→2층→3층 강등 📉
```

**왜 이렇게 할까?**
- 빠른 작업(채팅, 클릭 반응)은 바로바로 처리 → 사용자 경험 좋음!
- 느린 작업(다운로드, 압축)은 백그라운드에서 천천히 → 안 급함

### 3.5 🖥️ 실제 OS는 어떻게 할까?

```
피자를 N명이 나눠 먹는다면?
→ 각자 1/N 조각씩 먹는 게 공정!

"누가 가장 적게 먹었지?"

```

⌨️ 키보드 입력하면?

### 4.1 💼 취업/실무에서 어떻게 쓰이나요?

> "이론만 배우면 뭐해요, 실제로 어디 쓰이는데요?"
> 매우 좋은 질문입니다! 실제 예시를 봅시다.

#### 🎯 예시 1: "왜 내 프로그램이 느려요?"

면접 질문 또는 실무 상황:

```
👨‍💼 시니어: "API 응답이 5초나 걸려요. 개선해주세요."

😰 모르는 개발자:
"서버 성능이 안 좋나봐요..."

😎 아는 개발자:
"로그를 보니 CPU 사용률이 100%인데,
프로세스가 싱글 스레드로 돌고 있네요.
멀티스레드로 바꾸면 8배 빨라질 겁니다!"
```

#### 🎯 예시 2: 인턴/신입 과제에서

```python
# ❌ 모르면 이렇게 코딩
def download_images(urls):
    for url in urls:
        download(url)  # 100개 이미지, 100초 걸림 😭

# ✅ 알면 이렇게 코딩
import concurrent.futures

def download_images(urls):
    with concurrent.futures.ThreadPoolExecutor(max_workers=10) as pool:
        pool.map(download, urls)  # 100개 이미지, 10초! 🚀
```

**결과**: 같은 결과, 10배 빠른 코드 → **좋은 평가!**

### 4.2 🐍 파이썬 개발자라면 꼭 알아야 할 것

#### Python GIL (Global Interpreter Lock) 문제

```python
# ⚠️ 파이썬의 함정: GIL

# CPU 작업 (계산)
def heavy_calculation():
    return sum(i*i for i in range(10000000))

# 멀티스레딩으로 해봤자...
import threading
threads = [threading.Thread(target=heavy_calculation) for _ in range(4)]
# 결과: 싱글 스레드보다 오히려 느림! 😱

# 왜? 파이썬의 GIL이 "한 번에 하나의 스레드만" 실행하게 함
```

**해결책**:
```python
# ✅ CPU 작업은 멀티프로세싱!
import multiprocessing
with multiprocessing.Pool(4) as pool:
    results = pool.map(heavy_calculation, range(4))
# 결과: 4배 빨라짐! 🎉
```

**면접 팁**: "Python에서 CPU-bound 작업은 threading 대신 multiprocessing을 써야 합니다"

### 4.3 🌐 웹 개발자가 알아야 할 것

#### Node.js의 이벤트 루프

```javascript
// Node.js는 싱글 스레드인데 왜 빠를까?

// 🍳 요리사 한 명이 여러 요리 가능한 이유
// → "기다리는 동안" 다른 일을 함!

app.get('/api/data', async (req, res) => {
    // DB 조회 시작 (기다리는 동안 다른 요청 처리)
    const data = await db.query('SELECT * FROM users');
    res.json(data);
});

// 요청 1: DB 조회 시작 → 기다리는 중...
// 요청 2: 처리 시작!
// 요청 3: 처리 시작!
// 요청 1: DB 응답 왔다 → 완료!
```

**그래서**:
- I/O 작업(DB, 파일, 네트워크) → Node.js 강점
- CPU 작업(계산, 이미지 처리) → Node.js 약점

#### 무거운 작업은 Worker Threads로

```javascript
// 🎮 게임 서버에서 랭킹 계산 (무거운 작업)

// ❌ 메인 스레드에서 하면
app.get('/ranking', (req, res) => {
    const result = calculateRanking();  // 5초 걸림
    res.json(result);
});
// → 5초 동안 다른 모든 요청이 멈춤! 😱

// ✅ Worker Thread로 분리하면
const { Worker } = require('worker_threads');

app.get('/ranking', (req, res) => {
    const worker = new Worker('./ranking-worker.js');
    worker.on('message', (result) => res.json(result));
});
// → 계산하는 동안 다른 요청 정상 처리! ✨
```

#### JavaScript의 이벤트 루프와 Worker Threads

```javascript
// worker.js - CPU 집약적 작업
const { parentPort, workerData } = require('worker_threads');

function fibonacci(n) {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}

const result = fibonacci(workerData.n);
parentPort.postMessage(result);

// main.js - 메인 스레드
const { Worker } = require('worker_threads');
const express = require('express');
const app = express();

app.get('/fib/:n', (req, res) => {
    const n = parseInt(req.params.n);

    // Worker로 처리 → 메인 스레드 블로킹 없음!
    const worker = new Worker('./worker.js', {
        workerData: { n }
    });

    worker.on('message', (result) => {
        res.json({ n, result });
    });

    worker.on('error', (err) => {
        res.status(500).json({ error: err.message });
    });
});

app.listen(3000);
// 동시에 여러 요청 처리 가능!
```

### 4.4 ☁️ 클라우드/AWS에서는 어떻게 쓰이나요?

> "클라우드 엔지니어, DevOps 준비 중인데요"
> 이 개념들이 AWS에서 어떻게 적용되는지 봅시다!

#### 🐳 Docker/ECS = 프로세스 격리의 응용

```
┌────────────────────────────────────────────┐
│            EC2 인스턴스 (= 컴퓨터)           │
├────────────────────────────────────────────┤
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 컨테이너1 │  │ 컨테이너2 │  │ 컨테이너3 │  │

└────────────────────────────────────────────┘
```

**면접 질문**: "컨테이너와 VM의 차이가 뭔가요?"

```
VM (가상머신):
- 각자 독립된 OS 가짐
- 비유: 아예 다른 건물 🏢🏢

컨테이너:
- OS 커널 공유, 프로세스만 격리
- 비유: 같은 건물 내 다른 호실 🏠🏠
- 더 가볍고 빠름!
```

#### ⚡ Lambda = "미리 만들어둔 프로세스 풀"

```
[Lambda 콜드 스타트 = 새 프로세스 생성]

요청 왔다! → 새 환경 생성 (500ms~2초) → 처리
              ^^^^^^^^^^^^^^^^
              이게 "콜드 스타트"

[Lambda 웜 스타트 = 프로세스 재사용]

요청 왔다! → 기존 환경 재사용 (10ms) → 처리
              ^^^^^^^^^^^^^^^^^
              이게 "웜 스타트"
```

**실무 팁**: Lambda가 느리다면?
1. 메모리를 올려보세요 (CPU도 같이 올라감!)
2. Provisioned Concurrency로 미리 워밍해두세요

**❓ 문제 1: "서버가 느려요"**

```
[진단 과정]
1. CPU 확인 → 100%?
   → 멀티스레딩으로 분산 or 서버 추가

```

**❓ 문제 3: "멀티스레딩했는데 더 느려요"**

[원인 체크리스트]

□ 락 경쟁 심함? → 락 범위 줄이기
```

2️⃣ 한 프로그램의 여러 기능? → 스레드
3️⃣ 실패해도 다른 거 영향 없어야 한다? → 프로세스
4️⃣ 빠른 데이터 공유 필요? → 스레드
5️⃣ 모르겠다? → 일단 프로세스 (더 안전)
```

**Q2: "Python에서 멀티스레딩이 안 된다고요?"**

```
정확히는 "CPU 집약적 작업에서" 효과가 없어요.

GIL(Global Interpreter Lock) 때문에
Python은 한 번에 하나의 스레드만 Python 코드 실행 가능

하지만!
- 파일 다운로드, 웹 크롤링 (I/O 작업) → 스레딩 효과 있음!
- 무거운 계산 → multiprocessing 사용
```

**Q3: "컨텍스트 스위칭이 왜 중요해요?"**

```
비유: 책 바꿔 읽기

1권 읽다가 → 책갈피 끼우고 → 2권 꺼내서 → 어디까지 읽었지 확인

이 "바꾸는 시간"이 컨텍스트 스위칭!

너무 자주 바꾸면?
→ 바꾸는 시간 > 실제 읽는 시간
→ 비효율!

그래서 적절한 Time Quantum 설정이 중요해요.
```

### 💻 실습 코드 예시

**간단한 Python 예시: 싱글 vs 멀티**

```python
import time
from multiprocessing import Pool

def heavy_work(n):
    """무거운 계산 (소수 찾기)"""
    return sum(1 for i in range(2, n) if all(i % j != 0 for j in range(2, int(i**0.5)+1)))

# 싱글 프로세스
start = time.time()
results = [heavy_work(100000) for _ in range(4)]
print(f"싱글: {time.time() - start:.1f}초")  # 약 12초

# 멀티 프로세스 (4코어)
start = time.time()
with Pool(4) as p:
    results = p.map(heavy_work, [100000]*4)
print(f"멀티: {time.time() - start:.1f}초")  # 약 3초! (4배 빠름)
```

**JavaScript 예시: 비동기 처리**

```javascript
// ❌ 순차 처리 (느림)
async function slow() {
    const a = await fetch('/api/users');    // 1초
    const b = await fetch('/api/products'); // 1초
    const c = await fetch('/api/orders');   // 1초
    // 총 3초!
}

// ✅ 병렬 처리 (빠름)
async function fast() {
    const [a, b, c] = await Promise.all([
        fetch('/api/users'),
        fetch('/api/products'),
        fetch('/api/orders')
    ]);
    // 총 1초! (동시에 요청)
}
```
