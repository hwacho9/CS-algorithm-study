## 1. 멀티태스킹과 멀티프로세싱

### 1.1 단일 프로그램 실행의 한계

초창기 컴퓨터는 한 번에 하나의 프로그램만 실행했다.

```
프로그램 A 실행 → 완료 → 프로그램 B 실행 → 완료

문제: 음악 프로그램 끝나야 워드 실행 가능
```

이를 해결하기 위해 **멀티태스킹** 기술이 등장했다.

### 1.2 멀티태스킹 (Multitasking)

**하나의 CPU 코어**로 여러 프로그램을 동시에 실행하는 것처럼 보이게 하는 기술.

**핵심: 시분할 (Time Sharing)**

```
CPU가 약 0.01초(10ms) 단위로 프로그램을 번갈아 실행

프로그램A ──┬─────┬─────┬─────
프로그램B ──┴─────┴─────┴─────
           ↑     ↑     ↑
        10ms  10ms  10ms
```

- 각 프로그램의 실행 시간을 분할해서 마치 동시에 실행되는 것처럼 보이게 함
- CPU 코어가 하나만 있어도 여러 프로그램이 동시에 실행되는 것처럼 느낄 수 있음
- **소프트웨어(OS) 기반** 기술

### 1.3 멀티프로세싱 (Multiprocessing)

**여러 CPU 코어**를 사용하여 여러 작업을 물리적으로 동시에 처리하는 기술.

```
CPU 코어1: [프로그램 A 실행]
CPU 코어2: [프로그램 B 실행]
```

- **하드웨어 기반** 기술
- 진짜 동시에 실행됨 (병렬 처리)

### 1.4 멀티태스킹 vs 멀티프로세싱

| 구분 | 멀티태스킹 | 멀티프로세싱 |
|-----|---------|-----------|
| 관점 | 소프트웨어 (OS) | 하드웨어 (CPU) |
| 코어 수 | 1개로도 가능 | 2개 이상 필요 |
| 동시성 | 논리적 (Concurrent) | 물리적 (Parallel) |

**현대 컴퓨터는 둘 다 사용**

```
8코어 CPU에서 100개 프로세스 실행:
- 8개는 물리적으로 동시 실행 (멀티프로세싱)
- 나머지는 시분할로 번갈아 실행 (멀티태스킹)
```

## 2. 프로세스와 스레드

### 2.1 프로세스 (Process)

**실행 중인 프로그램의 인스턴스**

```
프로그램 (디스크의 파일) → 실행 → 프로세스 (메모리에 로드)
```

- 각 프로세스는 **독립적인 메모리 공간**을 가짐
- 프로세스끼리 서로의 메모리에 직접 접근 불가 (격리)
- 하나의 프로세스가 죽어도 다른 프로세스에 영향 없음

**프로세스 메모리 구성**

```
┌─────────────────────┐
│   Code (코드)        │  실행할 프로그램 코드
├─────────────────────┤
│   Data (데이터)      │  전역 변수, static 변수
├─────────────────────┤
│   Heap (힙)         │  동적 할당 메모리 (new, malloc)
├─────────────────────┤
│   Stack (스택)       │  지역 변수, 함수 호출
└─────────────────────┘
```

### 2.2 스레드 (Thread)

**프로세스 내에서 실행되는 작업의 단위**

- 프로세스는 최소 하나의 스레드를 가짐
- 한 프로세스 내에 여러 스레드가 존재할 수 있음
- 스레드는 프로세스가 제공하는 **메모리 공간을 공유**

![스레드 메모리 구조](./assets/Pasted%20image%2020260125012135.png)

**공유 vs 분리**

| 공유 | 분리 |
|-----|-----|
| Code | Stack |
| Data | 레지스터 |
| Heap | PC (Program Counter) |

### 2.3 프로세스 vs 스레드 비교

| 항목 | 프로세스 | 스레드 |
|-----|---------|-------|
| 메모리 | 독립적 | 공유 (Stack만 분리) |
| 생성 비용 | 높음 | 낮음 |
| 통신 | IPC 필요 (복잡) | 변수 공유 (간단) |
| 안정성 | 높음 (격리됨) | 낮음 (한 스레드 문제 → 전체 영향) |
| 컨텍스트 스위칭 | 느림 | 빠름 |

### 2.4 멀티스레드가 필요한 이유

하나의 프로그램 안에서도 동시에 여러 작업이 필요하다.

**워드 프로그램 예시**
- 스레드1: 문서 편집
- 스레드2: 자동 저장
- 스레드3: 맞춤법 검사

**유튜브 예시**
- 스레드1: 영상 재생
- 스레드2: 댓글 로딩

## 3. 스레드와 스케줄링

### 3.1 스케줄링이란?

**CPU에 어떤 스레드가 얼마만큼 실행될지 결정**하는 것.

- 운영체제가 담당
- 단순히 시간으로만 분할하지 않고, 다양한 우선순위와 최적화 기법 사용

### 3.2 단일 코어 스케줄링

운영체제는 **스케줄링 큐**를 가지고 있고, 각 스레드는 큐에서 대기한다.

```
[스케줄링 큐]
┌────────┬────────┬────────┐
│스레드A1 │스레드B1 │스레드B2 │ ──→ CPU 코어1
└────────┴────────┴────────┘

1. 스레드A1을 큐에서 꺼내서 CPU로 실행
2. 일정 시간 후, 스레드A1을 멈추고 다시 큐에 넣음
3. 스레드B1을 큐에서 꺼내서 CPU로 실행
4. 반복...
```

### 3.3 멀티 코어 스케줄링

CPU 코어가 2개 이상이면 더 많은 스레드를 물리적으로 동시 실행 가능.

```
[스케줄링 큐]
┌────────┬────────┬────────┐
│스레드A1 │스레드B1 │스레드B2 │
└────────┴────────┴────────┘
      ↓           ↓
  CPU 코어1    CPU 코어2
  [스레드A1]   [스레드B1]
```

### 3.4 주요 스케줄링 알고리즘

| 알고리즘 | 설명 | 특징 |
|---------|-----|------|
| **FCFS** | First Come First Served, 먼저 온 순서대로 | 단순함, Convoy Effect 문제 |
| **SJF** | Shortest Job First, 짧은 작업 먼저 | 평균 대기 시간 최소, 기아 현상 |
| **Round Robin** | 시간 할당량(Time Quantum)만큼 돌아가며 실행 | 공평함, 응답 시간 좋음 |
| **우선순위** | 우선순위가 높은 작업 먼저 | 중요 작업 먼저, 기아 현상 |
| **MLFQ** | 다단계 피드백 큐, 작업 특성에 따라 자동 조정 | 현대 OS에서 많이 사용 |

## 4. 컨텍스트 스위칭

### 4.1 컨텍스트 스위칭이란?

CPU가 현재 실행 중인 스레드를 멈추고 **다른 스레드로 전환**하는 과정.

```
스레드A 실행 중 → 멈춤 → 스레드A 상태 저장 → 스레드B 상태 로드 → 스레드B 실행
```

**저장/복원해야 하는 것 (컨텍스트)**
- Program Counter (다음 실행할 명령어 위치)
- CPU 레지스터 값들
- 스택 포인터
- 등등

### 4.2 컨텍스트 스위칭 비용

컨텍스트 스위칭은 **공짜가 아니다**.

**직접 비용**
- 컨텍스트 저장/복원 시간

**간접 비용 (더 큼)**
- CPU 캐시 무효화
- TLB 플러시 (프로세스 전환 시)

| 전환 종류 | 비용 |
|---------|-----|
| 스레드 전환 | 낮음 (메모리 공간 동일) |
| 프로세스 전환 | 높음 (TLB 비움 필요) |

### 4.3 멀티스레드가 항상 좋은가?

**아니다.** 컨텍스트 스위칭 비용 때문에.

```
[CPU 코어 2개, 1~10000 더하기]

멀티스레드:
- 스레드1: 1~5000
- 스레드2: 5001~10000
- 병렬 처리로 빠름 ✅

[CPU 코어 1개, 1~10000 더하기]

멀티스레드:
- 스레드1, 스레드2 번갈아 실행
- 컨텍스트 스위칭 비용 추가
- 싱글 스레드보다 느릴 수 있음 ❌
```

## 5. 실무 관점: CPU-바운드 vs I/O-바운드

### 5.1 작업의 두 가지 유형

| 유형 | 설명 | 예시 |
|-----|------|-----|
| **CPU-바운드** | CPU 연산이 많음 | 계산, 인코딩, 데이터 분석 |
| **I/O-바운드** | 대기 시간이 많음 | DB 조회, 파일 읽기, 네트워크 |

### 5.2 스레드 수 결정

**CPU-바운드 작업**
```
권장: 코어 수 + 1개

이유: CPU를 거의 100% 사용하므로 스레드를 CPU에 맞춤
```

**I/O-바운드 작업**
```
권장: 코어 수보다 훨씬 많이

이유: 스레드가 I/O 대기 중일 때 다른 스레드 실행
     → CPU가 놀지 않게
```

### 5.3 흔한 실수

```
❌ 상황: 웹 서버가 느림, CPU 사용률 4%
   원인: 4코어에 스레드 4개 (I/O 대기 중 CPU 놀고 있음)

❌ 잘못된 해결: 서버 장비 2배 업그레이드
   결과: CPU 사용률 2%, 여전히 느림

✅ 올바른 해결: 스레드 수 늘리기
   결과: CPU 활용도 증가, 처리량 증가
```

### 5.4 언어별 특성

| 언어 | 멀티스레딩 | 비고 |
|-----|----------|-----|
| **Python** | 제한적 | GIL 때문에 CPU 작업은 multiprocessing 사용 |
| **Java** | 좋음 | synchronized, ExecutorService |
| **JavaScript** | 싱글 스레드 | 이벤트 루프 + Worker Threads |
| **Go** | 매우 좋음 | 고루틴으로 쉽게 동시성 처리 |

**Python GIL 문제**
```python
# CPU 작업에서 멀티스레딩 효과 없음
# → multiprocessing 사용해야 함

from multiprocessing import Pool
with Pool(4) as p:
    results = p.map(heavy_calculation, data)
```

### 5.5 클라우드 환경 적용

이 개념들을 알면 AWS 리소스 성능 최적화에도 적용 가능.

| 서비스 | 작업 유형 | 최적화 포인트 |
|-------|---------|-------------|
| **Lambda** | CPU-바운드 | 메모리↑ (메모리에 비례해 CPU 할당) |
| **Lambda** | I/O-바운드 | 동시성↑, 메모리는 최소한으로 |
| **ECS/Fargate** | CPU-바운드 | vCPU 비율 높게 설정 |
| **ECS/Fargate** | I/O-바운드 | vCPU 낮추고 태스크 수↑ |
| **EC2** | CPU-바운드 | C계열 (Compute Optimized) |
| **EC2** | I/O-바운드 | 범용 인스턴스 + 스레드/프로세스 수↑ |

```
예시: API 서버 (I/O-바운드)

❌ c5.xlarge 1대 (4vCPU, 고성능)
   → CPU 사용률 5%, 비용 낭비

✅ t3.medium 2대 + 스레드 풀 확대
   → CPU 활용도↑, 비용↓, 처리량↑
```

## 정리

| 개념 | 핵심 |
|-----|------|
| 멀티태스킹 | 시분할로 동시 실행처럼 보이게 (SW) |
| 멀티프로세싱 | 여러 코어로 진짜 동시 실행 (HW) |
| 프로세스 | 독립된 메모리 공간, 격리됨 |
| 스레드 | 메모리 공유, 가볍고 빠름 |
| 스케줄링 | 어떤 스레드를 언제 실행할지 결정 |
| 컨텍스트 스위칭 | 스레드 전환 비용, 공짜 아님 |
