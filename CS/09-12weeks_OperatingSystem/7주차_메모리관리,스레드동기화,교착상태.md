## 1. 메모리 관리 개요

### 1.1 왜 메모리 관리가 필요한가?

여러 프로세스가 동시에 실행되려면 메모리를 효율적으로 나눠 써야 한다.

```
문제 상황:
- 물리 메모리: 4GB
- 프로세스 A: 2GB 필요
- 프로세스 B: 3GB 필요
- 총 5GB 필요 → 메모리 부족!
```

### 1.2 논리적 주소 vs 물리적 주소

#### 물리적 주소 (Physical Address)

**RAM의 실제 위치**. RAM을 거대한 사물함이라고 생각하면 된다.

```
RAM (8GB = 80억 개의 칸)
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│  0  │  1  │  2  │  3  │  4  │ ... │  N  │ N+1 │  ← 물리적 주소 (칸 번호)
├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
│ 데이터│ 데이터│ 데이터│ 데이터│ 데이터│ ... │ 데이터│ 데이터│  ← 각 칸에 1byte 저장
└─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

물리적 주소 0x50000 = RAM의 327,680번째 칸
```

> **참고: 0x 표기법**
> - `0x`는 16진수를 의미
> - 0x50000 (16진수) = 327,680 (10진수)
> - 메모리 주소는 2진수와 변환이 쉬운 16진수로 표기

#### 논리적 주소 (Logical Address / Virtual Address)

**프로세스가 보는 가상의 주소**. CPU가 생성하는 주소.

```
프로세스 A의 세계          프로세스 B의 세계
┌─────────────┐           ┌─────────────┐
│ 0x0000      │           │ 0x0000      │
│ 0x0500      │           │ 0x0500      │
│ 0x1000 ← x  │           │ 0x1000 ← y  │
│ 0x2000      │           │ 0x2000      │
└─────────────┘           └─────────────┘

A: "내 변수 x는 0x1000에 있어"
B: "내 변수 y도 0x1000에 있어"

→ 서로 다른 "세계"의 0x1000 (충돌 없음)
```

#### 실제 RAM에서는?

OS가 각 프로세스를 **다른 물리 위치**에 배치한다.

```
               물리 메모리 (RAM)
┌──────────────────────────────────────────┐
│ 0x00000 ~ 0x4FFFF : OS 영역              │
├──────────────────────────────────────────┤
│ 0x50000 ~ 0x7FFFF : 프로세스 A 영역       │
│         0x51000 ← A의 변수 x             │
├──────────────────────────────────────────┤
│ 0x80000 ~ 0xAFFFF : 프로세스 B 영역       │
│         0x81000 ← B의 변수 y             │
└──────────────────────────────────────────┘

프로세스 A가 "0x1000 읽어줘" → 실제 RAM 0x51000에서 읽음
프로세스 B가 "0x1000 읽어줘" → 실제 RAM 0x81000에서 읽음
```

#### 비유: 아파트 호수

| 개념 | 비유 |
|-----|------|
| 논리적 주소 | 아파트 **호수** (101호, 102호) |
| 물리적 주소 | 지구상 **GPS 좌표** |

```
A아파트 101호 주민: "나 101호 살아"
B아파트 101호 주민: "나도 101호 살아"

→ 둘 다 "101호"지만 실제 위치(GPS)는 완전히 다른 건물
```

#### 왜 분리하는가?

```
직접 물리주소를 쓰면 생기는 문제:

프로그램 A: "나는 RAM 0x1000~0x2000 쓸게"
프로그램 B: "나도 RAM 0x1000~0x2000 쓸게"

→ 충돌! 서로 데이터 덮어씀
→ 프로그래머가 수동으로 관리해야 함
→ 현실적으로 불가능
```

**장점**
- 프로세스 간 메모리 격리 (보안)
- 프로세스는 항상 0번지부터 시작한다고 생각하면 됨
- 실제 메모리 어디에 배치되든 프로세스는 신경 안 써도 됨

## 2. 주소 바인딩과 MMU

### 2.1 주소 바인딩 (Address Binding)

**프로그램이 메모리 어디에 올라갈지 결정하는 과정**.

#### 프로그램의 생애 주기

```
소스코드 작성 → 컴파일 → 실행파일 → 메모리에 로드 → 실행
                  ↑                    ↑            ↑
             Compile Time         Load Time     Run Time
```

| 시점 | 설명 | 비유 (영화) |
|-----|------|------------|
| **Compile Time** | 소스코드 → 실행파일 변환 | 영화 제작 |
| **Load Time** | 실행파일 → 메모리에 복사 | 필름을 영사기에 장착 |
| **Run Time** | 프로그램 실행 중 | 영화 상영 |

#### 바인딩 시점에 따른 분류

| 바인딩 시점 | 언제 주소 결정? | 특징 |
|------------|----------------|------|
| Compile Time | 컴파일할 때 | 주소 고정, 위치 바꾸려면 재컴파일 |
| Load Time | 메모리에 올릴 때 | 로더가 빈 자리 찾아서 결정 |
| **Run Time** | 실행 중 | 실행 도중에도 위치 변경 가능, **현대 방식** |

### 2.2 MMU (Memory Management Unit)

**논리주소 → 물리주소 변환을 담당하는 하드웨어**. CPU 안에 들어있는 칩.

```
┌─────────────────────────────────────┐
│                CPU                  │
│  ┌─────────┐      ┌─────────┐      │
│  │  코어   │ ───→ │   MMU   │ ───→ │ ───→ RAM
│  │         │      │ (변환기) │      │
│  └─────────┘      └─────────┘      │
│     논리주소          물리주소       │
│     0x1000     →     0x51000       │
└─────────────────────────────────────┘
```

#### 왜 하드웨어로 만들었나?

```
주소 변환은 매 메모리 접근마다 일어남
프로그램 한 줄 실행할 때도 수십 번 메모리 접근

→ 소프트웨어로 하면 너무 느림
→ 하드웨어(MMU)로 만들어서 초고속 처리
```

#### MMU가 하는 일

| 기능 | 설명 |
|-----|------|
| **주소 변환** | 논리주소 → 물리주소 |
| **메모리 보호** | 잘못된 주소 접근 차단 |
| **TLB 관리** | 자주 쓰는 변환 결과 캐싱 |

#### 메모리 보호 예시

```
프로세스 A: "0x1000 읽어줘"
MMU: "OK, 너의 0x1000은 물리주소 0x51000이야" ✅

프로세스 A: "0x99999999 읽어줘"
MMU: "그건 네 영역 밖이야!" ❌
→ Segmentation Fault 에러 발생
```

#### 비유

```
MMU = 통역사 + 경비원

통역사: 프로세스 언어(논리주소) → RAM 언어(물리주소) 변환
경비원: 허용된 영역만 접근 가능하게 감시
```

## 3. 페이징 (Paging)

### 3.1 페이징이란?

메모리를 **고정 크기 블록**으로 나누어 관리하는 기법.

```
가상 메모리          물리 메모리
┌─────────┐         ┌─────────┐
│ Page 0  │ ──────→ │ Frame 2 │
├─────────┤         ├─────────┤
│ Page 1  │ ──────→ │ Frame 0 │
├─────────┤         ├─────────┤
│ Page 2  │ ──────→ │ Frame 5 │
├─────────┤         ├─────────┤
│ Page 3  │ ──────→ │  Disk   │ (스왑)
└─────────┘         └─────────┘

- Page: 가상 메모리의 블록 (보통 4KB)
- Frame: 물리 메모리의 블록 (Page와 같은 크기)
- 순서 상관없이 흩어져 배치 가능
```

### 3.2 페이지 테이블 (Page Table)

가상 주소 → 물리 주소 매핑 정보를 저장하는 테이블.

```
┌────────┬────────┬───────┐
│ Page # │ Frame #│ Valid │
├────────┼────────┼───────┤
│   0    │   2    │   1   │
│   1    │   0    │   1   │
│   2    │   5    │   1   │
│   3    │   -    │   0   │  ← 디스크에 있음
└────────┴────────┴───────┘
```

### 3.3 주소 변환 과정

```
가상 주소: 0x00001234 (Page 1, Offset 0x234)

1. Page 번호 추출: 1
2. 페이지 테이블에서 Frame 번호 조회: 0
3. 물리 주소 계산: Frame 0 + Offset 0x234 = 0x00000234
```

### 3.4 페이지 폴트 (Page Fault)

접근하려는 페이지가 물리 메모리에 없을 때 발생.

```
1. CPU가 Page 3 접근 시도
2. Valid bit = 0 → 페이지 폴트 발생!
3. OS가 디스크에서 해당 페이지를 메모리로 로드
4. 페이지 테이블 업데이트
5. 명령어 재실행
```

**페이지 폴트는 비용이 크다**
- 메모리 접근: ~100ns
- 디스크 접근: ~10ms (10만 배 느림)

### 3.5 페이지 교체 알고리즘

물리 메모리가 가득 찼을 때, 어떤 페이지를 내보낼지 결정.

| 알고리즘 | 설명 | 특징 |
|---------|------|------|
| **FIFO** | 가장 먼저 들어온 페이지 교체 | 단순하지만 비효율적 |
| **LRU** | 가장 오래 사용 안 된 페이지 교체 | 효과적, 구현 복잡 |
| **LFU** | 가장 적게 사용된 페이지 교체 | 빈도 기반 |
| **Clock** | LRU 근사, 원형 큐 사용 | 실용적, Linux 사용 |

### 3.6 TLB (Translation Lookaside Buffer)

페이지 테이블 조회를 빠르게 하는 **캐시**.

```
가상 주소 → TLB 확인 → Hit? → 물리 주소
                    ↓ Miss
              페이지 테이블 조회
```

- TLB Hit: 매우 빠름 (~1 사이클)
- TLB Miss: 페이지 테이블 조회 필요 (느림)

### 3.7 단편화 (Fragmentation)

| 종류 | 설명 | 예시 |
|-----|------|------|
| **외부 단편화** | 총 공간은 충분하나 연속되지 않아 사용 불가 | [사용중][빈10KB][사용중][빈10KB] → 연속 15KB 요청 불가 |
| **내부 단편화** | 할당된 공간이 필요보다 커서 낭비 | 3KB 필요한데 4KB 블록 할당 → 1KB 낭비 |

**페이징의 장점**: 외부 단편화 없음 (고정 크기라서)
**페이징의 단점**: 내부 단편화 존재

## 4. 세그먼테이션 (Segmentation)

### 4.1 세그먼테이션이란?

메모리를 **논리적 단위**로 나누어 관리하는 기법.

```
┌─────────────────┐
│   Code Segment  │  프로그램 코드
├─────────────────┤
│   Data Segment  │  전역 변수
├─────────────────┤
│   Stack Segment │  지역 변수, 함수 호출
├─────────────────┤
│   Heap Segment  │  동적 할당
└─────────────────┘

각 세그먼트는 크기가 다를 수 있음
```

### 4.2 세그먼트 테이블

```
┌─────────┬──────────┬────────┐
│Segment #│  Base    │ Limit  │
├─────────┼──────────┼────────┤
│  Code   │ 0x1000   │ 0x400  │
│  Data   │ 0x2000   │ 0x300  │
│  Stack  │ 0x5000   │ 0x1000 │
└─────────┴──────────┴────────┘

- Base: 세그먼트 시작 주소
- Limit: 세그먼트 크기 (범위 체크용)
```

### 4.3 페이징 vs 세그먼테이션

| 항목 | 페이징 | 세그먼테이션 |
|-----|--------|-------------|
| 단위 크기 | 고정 (4KB) | 가변 |
| 단위 기준 | 물리적 | 논리적 (의미 단위) |
| 외부 단편화 | 없음 | 있음 |
| 내부 단편화 | 있음 | 없음 |

### 4.4 현대 시스템

대부분의 현대 OS는 **페이징**을 기본으로 사용.

## 5. 스레드 동기화

### 5.1 동기화가 필요한 이유

여러 스레드가 **공유 자원**에 동시 접근하면 문제 발생.

```java
// 공유 변수
int counter = 0;

// 스레드 1, 2가 동시에 실행
counter++;  // 이 연산은 원자적이지 않음!
```

**counter++ 실제 동작**
```
1. counter 값을 레지스터로 로드
2. 레지스터 값 +1
3. 레지스터 값을 counter에 저장
```

### 5.2 경쟁 조건 (Race Condition)

```
초기값: counter = 0, 기대 결과: 2

스레드1              스레드2
────────            ────────
LOAD counter (0)
                    LOAD counter (0)
ADD 1 (1)
                    ADD 1 (1)
STORE counter (1)
                    STORE counter (1)

결과: counter = 1  (기대값 2와 다름!)
```

### 5.3 임계 영역 (Critical Section)

**공유 자원에 접근하는 코드 영역**.

```
┌─────────────────────────────────┐
│       Entry Section            │  진입 허가 요청
├─────────────────────────────────┤
│       Critical Section         │  공유 자원 접근
├─────────────────────────────────┤
│       Exit Section             │  진입 허가 반납
├─────────────────────────────────┤
│       Remainder Section        │  나머지 코드
└─────────────────────────────────┘
```

**임계 영역 해결 조건**
1. **상호 배제 (Mutual Exclusion)**: 한 번에 하나의 스레드만 진입
2. **진행 (Progress)**: 임계 영역이 비어있으면 대기 중인 스레드가 진입 가능
3. **한정 대기 (Bounded Waiting)**: 무한 대기 방지

## 6. 세마포어와 뮤텍스

### 6.1 뮤텍스 (Mutex)

**Mutual Exclusion**의 약자. 한 번에 하나의 스레드만 접근 허용.

```
상태: locked / unlocked

┌────────────┐
│   Mutex    │ ← 열쇠가 1개뿐인 화장실
└────────────┘

스레드1: lock() → 사용 중 → unlock()
스레드2: lock() → 대기... → (스레드1이 unlock 후) → 진입
```

**코드 예시 (Python)**
```python
import threading

mutex = threading.Lock()
counter = 0

def increment():
    global counter
    mutex.acquire()    # lock
    try:
        counter += 1   # 임계 영역
    finally:
        mutex.release() # unlock
```

**코드 예시 (Java)**
```java
private final Object lock = new Object();
private int counter = 0;

public void increment() {
    synchronized(lock) {  // lock
        counter++;        // 임계 영역
    }                     // unlock (자동)
}
```

### 6.2 세마포어 (Semaphore)

**"동시에 몇 명까지 들어갈 수 있는지" 관리하는 카운터**.

#### 비유: 화장실

```
화장실 칸이 3개인 경우:

┌─────┬─────┬─────┐
│ 칸1 │ 칸2 │ 칸3 │   세마포어 = 3 (빈 칸 수)
└─────┴─────┴─────┘

사람1 입장 → 세마포어 = 2
사람2 입장 → 세마포어 = 1
사람3 입장 → 세마포어 = 0

사람4 도착 → 세마포어가 0이라 대기...
사람1 퇴장 → 세마포어 = 1 → 사람4 입장 가능!
```

#### 핵심 연산 2가지

```
wait() (또는 P):  들어가기 전에 호출
─────────────────────────────────
카운터 > 0  → 카운터 -1, 입장
카운터 == 0 → 대기 (누가 나올 때까지)


signal() (또는 V):  나올 때 호출
─────────────────────────────────
카운터 +1, 대기 중인 사람 깨움
```

#### 코드 예시 (Python)

```python
import threading

semaphore = threading.Semaphore(3)  # 동시에 3개까지 허용

def use_resource():
    semaphore.acquire()  # wait (카운터 -1)
    try:
        do_something()   # 리소스 사용
    finally:
        semaphore.release()  # signal (카운터 +1)
```

### 6.3 뮤텍스 vs 세마포어

| 항목 | 뮤텍스 | 세마포어 |
|-----|--------|---------|
| 카운터 | 1 (한 명만) | N (여러 명) |
| 비유 | 1인용 화장실 | N칸 화장실 |
| 동시 접근 | 1개만 | N개 가능 |
| 소유권 | 있음 (lock한 스레드만 unlock) | 없음 |
| 용도 | 상호 배제 | 리소스 풀 관리 |

```
뮤텍스 ≈ 세마포어(1)

세마포어(1): 한 번에 1명만
세마포어(3): 한 번에 3명까지
세마포어(10): 한 번에 10명까지
```

### 6.4 실무에서의 동기화

**데이터베이스 커넥션 풀**
```
DB 커넥션 10개만 가능:

semaphore = Semaphore(10)

스레드 100개가 동시에 DB 접근 시도
→ 10개만 접근, 나머지 90개는 대기
→ 1개 끝나면 대기 중 1개가 접근
```

**API Rate Limiting**
```
외부 API가 초당 5개 요청만 허용:

semaphore = Semaphore(5)

→ 동시에 5개만 요청
→ 응답 오면 다음 요청 진행
```

## 7. 교착상태 (Deadlock)

### 7.1 교착상태란?

두 개 이상의 스레드가 **서로 상대방이 가진 자원을 기다리며 영원히 대기**하는 상태.

```
스레드1: 자원 A 보유, 자원 B 대기
스레드2: 자원 B 보유, 자원 A 대기

→ 둘 다 영원히 대기 (Deadlock!)
```

**실생활 예시**
```
좁은 복도에서 마주친 두 사람:
- A: "당신이 먼저 지나가세요" (대기)
- B: "아니요, 당신이 먼저요" (대기)
→ 둘 다 영원히 서 있음
```

### 7.2 교착상태 발생 조건 (4가지 모두 만족 시)

| 조건 | 설명 |
|-----|------|
| **상호 배제** (Mutual Exclusion) | 자원을 한 번에 하나의 스레드만 사용 |
| **점유와 대기** (Hold and Wait) | 자원을 가진 채로 다른 자원 대기 |
| **비선점** (No Preemption) | 다른 스레드의 자원을 강제로 빼앗지 못함 |
| **순환 대기** (Circular Wait) | 스레드들이 원형으로 서로의 자원 대기 |

```
순환 대기 예시:

스레드1 → 자원A (보유) → 자원B (대기) →┐
                                      │
스레드2 → 자원B (보유) → 자원A (대기) ←┘
```

### 7.3 교착상태 예방 (Prevention)

**4가지 조건 중 하나를 원천 차단**

| 조건 | 예방 방법 | 단점 |
|-----|----------|------|
| 상호 배제 | 자원 공유 허용 | 대부분 불가능 |
| 점유와 대기 | 모든 자원을 한 번에 요청 | 자원 낭비 |
| 비선점 | 자원 강제 회수 허용 | 구현 복잡 |
| 순환 대기 | 자원에 순서 부여, 순서대로만 요청 | 제약 발생 |

**순환 대기 예방 코드**
```java
// 항상 자원 번호가 작은 것부터 lock
// 자원A=1, 자원B=2 라면

// 스레드1, 스레드2 모두:
lock(resourceA);  // 먼저
lock(resourceB);  // 나중
// 작업 수행
unlock(resourceB);
unlock(resourceA);

// → 순환 대기 불가능, 교착상태 예방!
```

### 7.4 교착상태 회피 (Avoidance)

**자원 할당 전에 안전한지 검사**

**은행원 알고리즘 (Banker's Algorithm)**
```
은행에 1000만원이 있고, 3명의 고객이 있다.

고객A: 최대 500만원 필요, 현재 200만원 대출
고객B: 최대 300만원 필요, 현재 100만원 대출
고객C: 최대 400만원 필요, 현재 200만원 대출

남은 돈: 500만원

새로운 대출 요청이 오면:
"이 요청을 승인해도 모든 고객이 최대 금액을 받을 수 있는가?"
→ Yes: 승인 (안전 상태)
→ No: 거절 (불안전 상태 → 교착상태 가능)
```

### 7.5 교착상태 탐지 및 복구 (Detection & Recovery)

**주기적으로 교착상태 검사 후 복구**

**탐지 방법**
- 자원 할당 그래프에서 사이클 탐지
- 타임아웃 기반 탐지

**복구 방법**
| 방법 | 설명 |
|-----|------|
| 프로세스 종료 | 교착상태 프로세스 강제 종료 |
| 자원 선점 | 자원 강제 회수 |
| 롤백 | 체크포인트로 되돌리기 |

### 7.6 교착상태 무시

**타조 알고리즘 (Ostrich Algorithm)**

```
"교착상태? 그냥 무시하자"

이유:
- 교착상태는 드물게 발생
- 예방/회피/탐지 비용이 큼
- 발생하면 재부팅

실제로 많은 OS가 이 방식 사용 (Linux, Windows)
```

### 7.7 실무에서의 교착상태: 데이터베이스 트랜잭션

#### 락(Lock)이란?

DB에서 데이터를 수정할 때 **다른 사람이 건드리지 못하게 잠금**.

```
UPDATE accounts WHERE id = 1
→ id=1 행을 "락" 걸음
→ 다른 트랜잭션은 이 행 수정 못함
→ 내가 끝나면 락 해제
```

#### 교착상태 발생 상황

```
계좌 테이블:
┌─────┬─────────┐
│ id  │ balance │
├─────┼─────────┤
│  1  │  1000원 │
│  2  │  1000원 │
└─────┴─────────┘

트랜잭션 1: 계좌1 → 계좌2로 100원 송금
트랜잭션 2: 계좌2 → 계좌1로 50원 송금
```

#### 교착상태 발생 과정 (시간순)

```
트랜잭션1                        트랜잭션2
────────                        ────────
① UPDATE id=1 (락 획득)
                                ② UPDATE id=2 (락 획득)
③ UPDATE id=2 하려는데...
   id=2는 트랜잭션2가 락 중
   → 대기...
                                ④ UPDATE id=1 하려는데...
                                   id=1은 트랜잭션1이 락 중
                                   → 대기...

결과: 둘 다 서로를 기다리며 영원히 대기 = 교착상태!
```

#### 그림으로 보면

```
트랜잭션1                    트랜잭션2
    │                           │
    ▼                           ▼
┌────────┐                 ┌────────┐
│ id=1   │ ←───── 대기 ────│        │
│ (락 중) │                 │        │
└────────┘                 └────────┘
    │                           │
    │        대기 ─────→   ┌────────┐
    │                      │ id=2   │
    └─────────────────────→│ (락 중) │
                           └────────┘

서로가 서로의 락을 기다림 → 교착상태!
```

#### 해결 방법: 락 순서 통일

**항상 id가 작은 것부터 락을 걸면 됨.**

```
트랜잭션1                        트랜잭션2
────────                        ────────
① UPDATE id=1 (락 획득)
                                ② UPDATE id=1 하려는데...
                                   트랜잭션1이 락 중
                                   → 대기...
③ UPDATE id=2 (락 획득)
④ 작업 완료, 락 해제
                                ⑤ 이제 id=1 락 획득
                                ⑥ UPDATE id=2 (락 획득)
                                ⑦ 작업 완료

→ 순서대로 진행되어 교착상태 없음!
```

#### 핵심

```
❌ 잘못된 방식:
   트랜잭션1: id=1 먼저 → id=2 나중
   트랜잭션2: id=2 먼저 → id=1 나중
   → 순서가 반대라서 교착상태 발생

✅ 올바른 방식:
   트랜잭션1: id=1 먼저 → id=2 나중
   트랜잭션2: id=1 먼저 → id=2 나중
   → 순서가 같아서 교착상태 없음
```

**"모두가 같은 순서로 락을 걸면 교착상태는 발생하지 않는다"**
